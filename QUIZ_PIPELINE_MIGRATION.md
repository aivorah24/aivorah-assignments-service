- **2026-09-12 — Diagnosed the "empty questions[]" gap flagged above, and found a FOURTH root cause**: `docx-to-pdf` was also hard-failing with `Navigation timeout of 30000 ms exceeded` on image-heavy Word docs (Puppeteer's `page.setContent` default 30s timeout, combined with Chromium counting mammoth's inlined base64 image data URIs as in-flight network requests for `networkidle0`) — fixed with an explicit 90s timeout, no other change. Separately, added `rasterizePdfPagesToImage` (pdfjs-dist + Puppeteer, same technique as the frontend's `pdfHelpers.ts`) so the PDF fallback could route through Qwen VISION instead of blind pdf-parse text. **This exposed the real cause of the empty-questions gap**: it is NOT a prompt-format mismatch — it's that asking Qwen to do the FULL one-shot structured-JSON quiz extraction (the same complex ~180-line prompt Gemini handles) is unreliable. Confirmed by rendering the actual worksheet image and visually verifying it has clear, readable numbered questions with blanks — yet full one-shot Qwen extraction returned empty `questions: []` for the Telugu fixture and empty `tasks: []` entirely for a second, unrelated real PDF. Separately, Qwen's Telugu-script OCR itself was found to hallucinate content (verified by comparing its transcription against the real rendered image — e.g. real text "దూర్ద ముగ్గులు బాగా పెదుతుంది" came back as fabricated nonsense "మారు మెచ్చును ఎంత నిశ్చయంగా"), a separate, non-Latin-script-specific accuracy limitation. **Fix**: stopped asking Qwen to structure the quiz at all — it's now used ONLY for OCR (transcribe visible text, its strength), and Groq's text model (already proven reliable at following this exact JSON-structuring prompt, used elsewhere in this codebase) builds the quiz from that transcribed text. **Live-verified with a synthetic English math worksheet PDF** (real embedded text, no OCR needed): title, both tasks, and all 5 questions came back fully correct, including correct computed answers and step-by-step solutions — confirming the Groq-structuring half of the pipeline is fully reliable when given real, accurate source text. Note: the simpler worksheet-METADATA extraction prompt (`extract-questions-async`, title/chapter/subject/learning-outcomes) was NOT changed — it's short enough that Qwen handles it reliably in one shot, already live-verified working correctly end to end.
- **2026-09-12 — OCR provider benchmark (Telugu-script accuracy)**: per an explicit directive not to keep patching Qwen indefinitely, benchmarked alternatives against the real rendered Telugu worksheet image. No dedicated OCR credentials (Google Cloud Vision, Azure Vision, AWS Textract, ABBYY, OCR.space) exist anywhere across all 19 repos — confirmed by search; provisioning one would need a new account/billing decision. **Tesseract.js (`tesseract.js@7`, WASM, MIT-licensed, runs fully local — no API key, no network call, no per-request cost)** was tested with the `tel+eng` trained-data pack against the same real rendered image Qwen hallucinated on: it transcribed "దుర్గ ముగ్గులు బాగా పెడుతుంది" correctly (verified word-for-word against the source image), versus Qwen's fabricated "మారు మెచ్చును ఎంత నిశ్చయంగా" — a dramatic accuracy improvement, at ~7.5s per page (single CPU, no GPU) with no billing/latency/availability dependency on an external API. Minor noise on decorative/blank-line regions (stray Latin-letter artifacts) was observed but didn't corrupt the real Telugu text.
- **2026-09-12 — Implemented Tesseract.js as the script-aware OCR engine for Indic scripts.** `Tesseract.detect()` (OSD mode, no full OCR pass - cheap to run up front) reliably identifies the script directly from the image itself, with zero prior text needed - so it works the same for a bare image upload or a rasterized PDF page. `detectScriptLang` maps the detected script (Telugu/Devanagari/Tamil/Kannada/Malayalam/Bengali/Gujarati/Gurmukhi/Oriya) to its Tesseract language code, defaulting to `'eng'` (keeping Qwen as the OCR engine, unchanged) on any detection failure or Latin/unrecognized script - Tesseract only ever ADDS coverage, never removes Qwen's. `callOcrText` is the resulting router: Tesseract for detected non-Latin scripts, Qwen for Latin/English, with the other engine tried as a safety-net if the first throws. Wired into both `generateQuizFromPdf`'s fallback (`callGroqTextVisionFallback`) and, since the same one-shot-structuring unreliability applied there too, `generateQuizFromImage`'s fallback (previously full Qwen one-shot structuring - now OCR + Groq-structure, same as the PDF path). **A second Indic language was tested per the acceptance criteria**: a full-page synthetic Hindi/Devanagari worksheet (grammar exercise, verb identification, fill-in-the-blank, antonyms) was correctly detected as `hin` and transcribed with high accuracy (only 2 minor word-level errors out of ~10 lines of real text) - a dramatic improvement over Qwen's complete hallucination on Telugu. **A real crash-safety bug was found and fixed during this work**: tesseract.js has an undocumented failure mode where a genuinely undecodable buffer (not just an unusual format - garbage bytes) makes its underlying worker emit a Node `'error'` event that escapes the returned promise entirely and crashes the whole Node process, even from inside a try/catch around `Tesseract.detect`/`recognize` (verified live: a corrupt-upload test case took down the process). Fixed with `looksLikeDecodableImage` - a magic-byte check (PNG/JPEG/WebP/BMP signatures) that runs before any buffer reaches Tesseract at all, so genuinely corrupt input is rejected as a normal, catchable error instead. This satisfies the "OCR failure must be handled safely" requirement more strictly than originally scoped - it's not just try/catch around the OCR call, it's preventing a known process-crash path entirely. 206/206 tests passing (10 new: `tests/unit/ocrRouting.test.js`; 2 existing tests in `quizGenerateImage.test.js` updated for the new OCR-based fallback architecture, since fake test bytes now correctly fail the same decodability guard real corrupt uploads would).
- **2026-09-12 — Found a FIFTH root cause via live manual-tester report, applicable to ANY document/task type**: a real English math worksheet's "Compare fractions with <, >, or =" task came back with a title but zero questions in its published interactive quiz — not a Telugu/OCR issue (English, Latin script), and not matched by any of `quizHtmlRenderer.js`'s table-building normalizers (audited `normalizeRiddleTables`, `normalizeLetterGridTables`, `normalizeTables` — none fire on comparison-style phrasing, and none had a code path that could zero out a task's `questions` without also setting a replacement `table`). Conclusion: the generation step itself sometimes produces a task title with no items, for arbitrary task types/phrasing — since any uploaded document can contain any task type, this can't be fixed one task-type at a time. **Fix**: added a general completeness check (`findIncompleteTasks` in `services/quizVision.js`) that flags any task with a title but no questions AND no table/tables/chart/pyramids/diagramFillBlanks, then does exactly one retry (`retryIncompleteTasks`) against whichever engine actually produced the quiz (Gemini, or the Groq-text/Qwen-OCR fallback), asking specifically for the missing tasks by title, merged back in by position (with a fuzzy-title fallback, since models reliably drop "Task N:" prefixes even when told to echo the title exactly — caught live during testing and fixed before shipping). Wired into both `generateQuizFromImage` and `generateQuizFromPdf`. **Live-verified with a real retry call**: a mocked "Compare fractions" gap was correctly re-populated with 2 fully-solved comparison questions (correct `<`/`>` answers and worked solutions) via a real Groq call. 9 new unit tests added (`tests/unit/quizVisionRetry.test.js`); full suite 195/195 passing.
